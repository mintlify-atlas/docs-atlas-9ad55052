Viajes AJT applies a defense-in-depth approach: every request passes through multiple independent security layers before any application logic runs. Security headers are applied before routing, CSRF tokens are validated before controller dispatch, and database queries always use PDO prepared statements. This page documents each layer in detail.

---

## CSRF Protection

Cross-site request forgery protection is implemented in the `App\Helper\Csrf` class and enforced globally in `public/index.php` before any route is dispatched.

### Token Generation

`Csrf::token()` generates a 64-character hexadecimal token using cryptographically secure randomness and stores it in the session:

```php
public static function token(): string
{
    if (session_status() === PHP_SESSION_NONE) {
        session_start();
    }

    if (empty($_SESSION['csrf_token'])) {
        $_SESSION['csrf_token'] = bin2hex(random_bytes(32));
    }

    return $_SESSION['csrf_token'];
}
```

`random_bytes(32)` produces 32 bytes of CSPRNG output; `bin2hex` encodes it to a 64-character string. The token persists in the session for the life of the session — it is not rotated per request.

### Embedding in Forms

`Csrf::field()` returns a ready-to-use hidden input element:

```php
public static function field(): string
{
    return '<input type="hidden" name="csrf_token" value="' . self::token() . '">';
}
```

All HTML forms in Viajes AJT include `<?= Csrf::field() ?>` to embed the token.

### Verification

`Csrf::verify(string $token)` uses `hash_equals()` for timing-safe comparison, preventing timing side-channel attacks:

```php
public static function verify(string $token): bool
{
    $storedToken = $_SESSION['csrf_token'] ?? '';

    if ($storedToken === '') {
        return false;
    }

    return hash_equals($storedToken, $token);
}
```

### Controller-Level Shortcut

`Csrf::validate(string $redirect = '/')` reads `$_POST['csrf_token']` and redirects to `$redirect` if verification fails — a one-liner for use in controller POST methods:

```php
public static function validate(string $redirect = '/'): void
{
    $token = $_POST['csrf_token'] ?? '';

    if (!self::verify($token)) {
        $_SESSION['error'] = 'Token CSRF inválido. Por favor, intente nuevamente.';
        header('Location: ' . (defined('BASE_URL') ? BASE_URL : '') . $redirect);
        exit();
    }
}
```

### Global Enforcement in index.php

Before `Router::dispatch()` is called, `index.php` verifies the CSRF token for **every POST request** regardless of route:

```php
if (PHP_SAPI !== 'cli' && ($_SERVER['REQUEST_METHOD'] ?? '') === 'POST') {
    $token = $_POST['csrf_token'] ?? null;
    if (!Csrf::verifyToken($token)) {
        http_response_code(403);
        // Renders a 403 HTML page and exits
    }
}
```

A request with a missing, empty, or mismatched token receives HTTP 403 and never reaches a controller.

<Warning>
  `Csrf::verifyToken()` is marked `@deprecated` — it is an alias of `verify()` kept for backwards compatibility. New controller code should call `Csrf::verify()` or `Csrf::validate()` directly.
</Warning>

## HTTP Security Headers

`SecurityHeaders::apply()` is called at the very top of every request, before session start or routing. It sets the following headers:

### Standard Headers

| Header | Value | Purpose |
|---|---|---|
| `X-Content-Type-Options` | `nosniff` | Prevents MIME-type sniffing attacks |
| `X-Frame-Options` | `SAMEORIGIN` | Blocks the page from being loaded in a cross-origin `<iframe>` |
| `X-XSS-Protection` | `1; mode=block` | Enables XSS filter in older browsers |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | Limits referrer information sent to third-party origins |
| `Permissions-Policy` | `geolocation=(), microphone=(), camera=(), payment=()` | Disables browser APIs that are not used by the application |

### HSTS (HTTPS only)

When the request arrives over HTTPS, the following header is added:

```
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
```

This instructs browsers to enforce HTTPS for one year, including all subdomains, and allows submission to browser preload lists.

### Content Security Policy

A per-request **nonce** (`base64_encode(random_bytes(16))`) is generated by `SecurityHeaders::getNonce()` and embedded in the CSP header. Inline scripts must carry the matching `nonce` attribute to execute.

```
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-{nonce}' https://code.jquery.com
             https://cdn.jsdelivr.net https://stackpath.bootstrapcdn.com;
  style-src 'self' 'unsafe-inline' https://fonts.googleapis.com
            https://cdn.jsdelivr.net https://stackpath.bootstrapcdn.com;
  font-src 'self' https://fonts.gstatic.com https://cdn.jsdelivr.net;
  img-src 'self' data: https:;
  connect-src 'self' https://*.tile.openstreetmap.org;
  frame-src 'self' https://www.openstreetmap.org;
  frame-ancestors 'self';
  form-action 'self';
  base-uri 'self'
```

<Note>
  `style-src` includes `'unsafe-inline'` to accommodate Bootstrap and jQuery UI inline styles injected at runtime. All other directives are restrictive by default.
</Note>

## Password Security

Viajes AJT never stores or logs passwords in plain text. All passwords are hashed using PHP's built-in bcrypt implementation at registration and login:

```php
// Registration — hash before insert
$passwordHash = password_hash($password, PASSWORD_BCRYPT);

// Login — verify against stored hash
if ($user && password_verify($password, $user['password_hash'])) {
    // Authenticated
}
```

`PASSWORD_BCRYPT` applies the bcrypt algorithm with a cost factor of 10 (PHP's default). The resulting hash is stored in `usuarios.password_hash` (VARCHAR 255) and is never returned to the client.

## Session Security

Sessions are configured in `index.php` before `session_start()` is called:

```php
session_name('VIAJESAJTSESSID');

session_set_cookie_params([
    'lifetime' => 0,           // Session cookie — expires when browser closes
    'path'     => '/',
    'httponly' => true,        // Inaccessible to JavaScript
    'secure'   => !empty($_SERVER['HTTPS']) && $_SERVER['HTTPS'] !== 'off',
    'samesite' => 'Lax',       // Blocks CSRF from cross-site navigations
]);
```

In addition:

- **`session_regenerate_id(true)`** is called on both successful login and successful registration, preventing session fixation attacks. The old session file is deleted (`true` argument).
- The session cookie name `VIAJESAJTSESSID` avoids exposing the PHP version via the default `PHPSESSID` name.
- `samesite=Lax` ensures the session cookie is not sent on cross-origin POST requests from other sites.

## Role-Based Access Control

The application has two roles:

<CardGroup cols={2}>
  <Card title="Role 1 — Client" icon="user">
    Standard registered user. Can browse the catalog, create bookings, manage their own profile, view their reservations, and submit visa advisory requests.
  </Card>
  <Card title="Role 2 — Admin" icon="shield">
    Full administrative access. Can manage packages, view all reservations and users, change booking statuses, export data, and configure payment settings.
  </Card>

### Admin Route Protection

`AdminController.__construct()` verifies `$_SESSION['usuario']['id_rol'] === 2` on every admin request. Any client or unauthenticated user attempting to access an `admin/*` route is redirected immediately.

### BaseController Helper

For granular checks outside `AdminController`, any controller can call the inherited `getDashboardPath()` or implement role checks before rendering:

```php
// Redirect to appropriate dashboard based on role
$this->redirect($this->getDashboardPath((int)$_SESSION['usuario']['id_rol']));
// id_rol = 2 → /admin/dashboard
// id_rol = 1 → /profile/mi-perfil
```

## Error Handling

`ErrorHandler::register(bool $debug)` is called at bootstrap with `$debug = LocalConfig::APP_DEBUG` (`false` in production).

<Tabs>
  <Tab title="Production (APP_DEBUG = false)">
    - `display_errors` is set to `'0'`
    - Exceptions are caught, logged to `storage/logs/error-YYYY-MM-DD.log` and `storage/logs/error.log`
    - The user sees a clean error page rendered from `app/Views/errors/500.php`
    - No stack traces, file paths, or internal messages are exposed to the browser
  </Tab>
  <Tab title="Development (APP_DEBUG = true)">
    - `display_errors` is set to `'1'`
    - Uncaught exceptions render a full HTML debug page with exception class, message, file, line, and stack trace
    - Fatal errors detected in the shutdown handler also produce a visible error page
  </Tab>
</Tabs>

Custom error views exist for the three most common HTTP error codes:

| Code | View file | Trigger |
|---|---|---|
| 404 | `app/Views/errors/404.php` | No matching route in `Router::dispatch()` |
| 429 | `app/Views/errors/429.php` | Rate limit exceeded (HTML response path) |
| 500 | `app/Views/errors/500.php` | Uncaught exception or fatal error in production |

## PDO Prepared Statements

All database queries in Viajes AJT use PDO bound parameters. The connection is initialized with `PDO::ATTR_EMULATE_PREPARES => false`, which forces the MySQL driver to use true server-side prepared statements — preventing any SQL injection through type coercion edge cases in the emulation layer:

```php
$stmt = $db->prepare(
    "SELECT * FROM usuarios WHERE email = :email"
);
$stmt->execute([':email' => $email]);
$user = $stmt->fetch();
```

No raw interpolation of user input into SQL strings exists anywhere in the codebase.

## Input Validation

Server-side validation is performed in every controller method that processes user input before any database operation. Common validations include:

- Required field checks (`trim()` + empty string comparison)
- Email format validation (`filter_var($email, FILTER_VALIDATE_EMAIL)`)
- Integer range validation for passenger counts and numeric IDs
- File upload validation (MIME type and size checks in `PaqueteController`)

Client-side HTML5 validation (`required`, `type="email"`, etc.) is present in all forms as a UX aid but is **never relied upon** for security — all validation is duplicated on the server.
